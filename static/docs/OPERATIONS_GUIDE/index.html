    MFFM Operations Guide — a step-by-step manual for a human maintainer¶

    This is the single entry point for keeping the Monetary–Financial–Fiscal Macromodel (MFFM) tool running: how to update the data each quarter, add a new data series, add a new economy, test everything before a deployment, and deploy to production. It is written to be followed top to bottom by a human who did not build the tool. Each part gives the exact commands; where a task has deep detail, it points to the specialist document rather than duplicating it.

    Two golden rules that override everything below. 1. Never ship fabricated data. Every number is either a genuine source observation or a model-implied value produced by the G-BVAR framework and recorded as such. If a series cannot be sourced, you drop it or truncate to the genuine edge — you never invent, back-fill, or extrapolate a value to fill a gap. (See docs/synthetic-data-audit.md.) 2. Never deploy to production without an explicit go-ahead. Production is the bvarscenario repo's main branch. A push there is public and cached by a CDN. Do not push it on your own initiative; confirm first, every time.

    Part 0 — The mental model (read once)¶

    The tool estimates the models once and shifts them forward each quarter. There are therefore two different maintenance events:

    • Within-year quarterly shift (the common one — Part 1). New data has arrived; you move the panel forward one quarter and let the coupled G-BVAR nowcast every cell that isn't yet observed. No re-estimation — the estimated coefficients (the "companion") are frozen.
    • Annual re-estimation (rare — Part 6). Once a year, or whenever the variable set changes (Part 2, Case B), you re-estimate the whole coupled system on the final data.

    Each bloc's history is stored in historical_levels.json as a T×n matrix. Log variables are held as 100·log(level); linear variables (rates, ratios) as-is. The forecast x-axis is numeric offsets: x = −1 is the last observation, x = 0 is the first forecast (see app/src/lib/dates.ts). The one load-bearing date constant is DEFAULT_LAST_HIST_DATE in that file — the shift moves it last.

    Deployment is a two-hop chain, not a single push: bvarscenario/main → a GitHub Actions build → the starter-hugo-academic repo → GitHub Pages, then a CDN. Budget ~25 minutes and verify against a file that actually changed (Part 5) — the first 200 you get back can be a stale cache.

    Part 1 — Update the dataset each quarter (the within-year shift)¶

    Run this when a new quarter's data is out (advanced economies first; financials are always available). It moves every bloc forward one quarter, pulls genuine observations where they exist, and fills the rest with a cross-block G-BVAR nowcast whose provenance is recorded cell by cell.

    Step 1 — Is a shift due? 

    npm run data:check           # probes the release calendar
# exit 10 = a quarterly shift is due; exit 11 = an annual re-estimation is due; 0 = nothing due

    Step 2 — Dry-run the whole shift (writes nothing). This runs every source gate and the full coupled solve but does not touch any file. Read its output; make sure the gates pass and the seam looks sane. 

    npm run data:shift -- --dry-run

    Step 3 — Commit the shift. This archives the current vintage, then runs the full publish chain. 

    npm run data:shift
    The chain (in order): archive the current vintage → build the counterfactual baseline → pull genuine observed rows for the wired leaders (gate-then-write; revisions are accepted as new knowledge) → apply realized-data pins for the mirror blocs (gated; a pin that fails its sanity gate falls back to the nowcast, never to a made-up number) → cross-block G-BVAR nowcast completion of every remaining cell → publish the staged panel → extend the euro members one row each → re-simulate the predictive bands → rebuild the coverage manifest → bump DEFAULT_LAST_HIST_DATE → rebuild the manifest again (so it is labelled on the new grid) → run the cut-off verification gate.

    Step 4 — Verify (Part 4). At minimum: node scripts/verify_cutoffs.mjs must print cutoffs OK.

    If the chain stops half-way (hiccup recovery). Every step is idempotent — the whole chain is safe to re-run from the top. Never hand-edit a shipped panel to "finish" it: the gate treats a null tail as what it is, an incomplete run. To roll back, restore from pipeline/vintages/<the archived vintage>/. Full detail, per-step recovery, and exit-code meanings: docs/data-refresh-rollout.md.

    Part 2 — Add a new data series to an existing bloc¶

    First decide which of two kinds it is, because the effort is completely different.

    Case A — a DERIVED series (no re-estimation)¶

    A derived series is an accounting identity on top of variables the model already estimates — e.g. the fiscal block (primary balance, debt) from revenue/expenditure/rate, or the external block (trade balance, current account, NFA) from exports/imports/GDP/FX. Because nothing new enters the VAR, you do not re-estimate. Steps:

    1. Source the real seed and any parameters. A derived stock (debt, NFA) needs a real, sourced starting value — e.g. nfa0 = net IIP / nominal GDP from a national source. Record the source string in the meta file. Modeling constants that are not sourced (e.g. an imputed return) are shipped with a _flags: "... MODELING DEFAULT ..." note, never presented as estimated.
    2. Write the per-bloc meta file — fiscal_meta.json or external_meta.json in app/public/data/bvar/<CC>/, following an existing one (US is the reference). It holds idx (the column indices of the driver variables, resolved by variable id), the real seed, and the flagged defaults.
    3. The compute is already generic — computeFiscalBlock / computeExternalBlock in app/src/lib/compute/. If the new bloc's units differ (e.g. trade in USD, GDP in local currency), set the units factors in the meta (see the header of externalAccounting.ts) — never a fabricated conversion; a bloc whose units can't be reconciled ships without the block.
    4. Validate the anchor against the published figure (e.g. the trade balance at the nowcast should sit in the published BoP range). Add or extend a fixture test in app/src/__tests__/compute/…Accounting.test.ts.
    5. The chart section (external, fiscal) picks the series up automatically once the meta exists.

    Case B — an ESTIMATED series (requires re-estimation)¶

    An estimated series enters the VAR — e.g. re-adding a nominal effective exchange rate (NEER), or a new credit series. This changes a bloc's variable count, which changes the coupling dimension, so it requires one combined re-estimation of the coupled system. Steps:

    1. Source it with a fetcher in pipeline/ (copy the closest fetch_*.py / build_*.py; keep the aggregation_method=avg monthly→quarterly convention — quarterly values are period averages, not end-of-period). Stage the series where the panel builder expects it (e.g. NEER goes to <staging>/neer/NEER_<CC>.json, per build_newbloc_panel.py).
    2. Add it to the panel builder — the bloc's variable list in pipeline/build_gvar_2025q4.py — and to the bloc's spec.json variable list (id, label, transformation log/lin).
    3. Rebuild the panel, then re-estimate (Part 6). The GVAR-EM estimator is pipeline/export_bvar_gvar24_loop.m; it re-fits the coupled system. Follow docs/REESTIMATING_MODELS.md exactly — the scaling conventions there are load-bearing.
    4. Regenerate the coupling artifact (app/public/data/bvar/gvar/coupling_default.json.gz) — the pre-computed (I−M)⁻¹ the browser solves with. This is mandatory: computing it in-browser takes ~20 minutes.
    5. Shift to the current quarter (Part 1) so the newly-estimated vintage carries a live nowcast.
    6. Verify (Part 4), including a re-derivation of any MATLAB golden that depends on the changed bloc (see Part 4, step 6).

    The no-synthetic rule applies at every step: if the new series is not genuinely available for a bloc, that bloc gets the series truncated to its real edge or omitted — you do not pad it.

    Part 3 — Add a new economy (bloc)¶

    A new bloc is a bigger version of Part 2, Case B: source its full variable set, build its panel, add it to the GVAR topology and the trade-weights matrix, re-estimate the coupled system, and regenerate the coupling artifact. The full, tested procedure is in docs/ADDING_A_COUNTRY.md — follow it end-to-end; the trade-weights and star-variable steps are easy to get subtly wrong.

    Part 4 — Test before deployment (the full gate)¶

    Run these in order. The deployment is cleared only when the type-check, both test suites, and the cut-off gate are green. Do not use npm run test:all to make a pass/fail decision — it runs the heavy GVAR tests in parallel workers where they time out; that is a harness artifact, not a real failure.

    1. Type-check. 

    npx tsc --noEmit          # must exit 0

    2. Fast unit suite (everything except the heavy coupled-GVAR tests). 

    npm test                  # must be green

    3. Heavy GVAR suite — run SEPARATELY and SERIALLY. These validate the coupled solve (closed-form == iterative, RoW↔US feedback, per-draw bands) and are compute-heavy; they only pass with one worker. 

    npm run test:heavy        # must be green (takes several minutes; a single band test can take ~80s)

    4. Cut-off gate (proves dates.ts == manifest == on-disk rows, no null tails, provenance converged). 

    node scripts/verify_cutoffs.mjs     # must print "cutoffs OK: … blocs end <quarter> …"

    5. Data-consistency audit (run after any data shift). Confirms the shift froze history (rows before the new quarter are byte-identical to the pre-shift vintage) and that every cell of the new quarter is one of exactly three kinds — a genuine observation, a gated realized pin, or a G-BVAR imputation recorded in nowcast_provenance.json — with nothing unexplained. The pattern: compare app/public/data/bvar/<CC>/historical_levels.json against pipeline/vintages/<pre-shift>/…, and check each last-row cell against pipeline/realized_pins_<Q>.json and the provenance imputedMask. (Small value revisions in the recent fiscal/credit tail are expected and accepted; a null→value change or a deep-history rewrite is a red flag.)

    6. Paper/manual compile (only if you edited docs/). 

    cd docs/paper && pdflatex -interaction=nonstopmode mffm_platform_paper.tex && pdflatex … mffm_platform_paper.tex
# check the log for "undefined reference" or "Undefined control sequence" — there must be none.

    Two known, benign test gotchas (and how to clear them)¶

    • Slow "real US posterior draws" tests (longRunTilt): these process every posterior draw at H=40 and legitimately take 10–20s. They carry an explicit 60000 ms timeout. If a machine is very loaded they can still be slow — that is a timeout, not a logic failure.
    • MATLAB golden re-derivation (scenario-scale-convention): this test pins the tool's conditional forecast against an independent MATLAB conforekf ground truth. Whenever the US bloc is re-estimated, the golden must be re-derived, or the test will fail on a stale reference: 
      cd pipeline/_verify && octave --no-gui --eval "source('gt.m')"     # reads the CURRENT companion
      then copy the infl_corr array from pipeline/_verify/gt_testvals.json into MATLAB_INFL_CORRECT in app/src/__tests__/compute/scenario-scale-convention.test.ts. gt.m resolves columns by variable id, so it is robust to re-estimation. This is a fix (refresh the reference), not a code change — the tool and MATLAB agree to ~1e-6 on the current model.

    Green bar = tsc clean and npm test green and npm run test:heavy green and verify_cutoffs OK and (after a shift) the consistency audit clean.

    Part 5 — Deploy to production¶

    Only after the green bar in Part 4 and an explicit go-ahead. Production overwrites the public site.

    1. Commit the changes on your working branch (improve-live), with a clear message.

    2. Build the static export. 

    npm run build            # → app/out/  (the static site)

    3. Push to production. Production is the bvarscenario remote's main. Push your branch's built state there per the project's deploy convention (a fast-forward of main).

    4. Wait for the two-hop build. bvarscenario/main triggers a GitHub Actions build that publishes to the starter-hugo-academic repo, which GitHub Pages serves. Budget ~15 minutes for the build and ~10 minutes more for the CDN's 404-cache to expire.

    5. Verify against a file that actually changed. Do not trust the coverage manifest (it can look right while the bundle is stale — this has caused a false "confirmed" before). Poll a vintage-discriminating file, e.g. Hong Kong's spec.json or the euro-area spec.json (seasonalRows: 3): 

    curl -s https://matyasfarkas.github.io/bvar-scenario/data/bvar/HK/spec.json | head -c 200
    Confirm it shows the new content before you call the deploy done.

    Rollback. If production is wrong, re-deploy the previous good commit the same way (build → push → verify). The vintage archive in pipeline/vintages/ lets you rebuild any prior data state.

    Full deploy-verification notes: docs/data-refresh-rollout.md → "Deploy verification".

    Part 6 — Annual re-estimation (reference)¶

    Once a year (or after a Part 2 Case B change), re-estimate on the final data: 

    npm run data:q1prep      # stages the annual re-estimation prep (see its output for the manual steps)
    Then run the MATLAB estimator (pipeline/export_bvar_gvar24_loop.m), regenerate the coupling artifact, and shift to the current quarter (Part 1). The exact per-bloc sequence, the scaling conventions, and the post-run checklist are in docs/REESTIMATING_MODELS.md. Set DEFAULT_LAST_HIST_DATE to the estimation vintage before the shift; the shift moves it forward again.

    Appendix B — Guardrails (the hard rules, restated)¶

    1. No synthetic data. Source it, or drop/truncate to the genuine edge. Flag every modeling default; record every source.
    2. No production deploy without an explicit go-ahead.
    3. Never hand-edit a shipped panel to patch a gap — re-run the (idempotent) chain instead.
    4. Quarterly values are period averages (aggregation_method=avg), not end-of-period.
    5. The coupled solve aligns blocs by projection step, not by calendar date — keep the panel on a uniform row grid; never leave one bloc a row short.
    6. Decide derived vs estimated before adding a series (Part 2): derived is data-only; estimated forces a re-estimation.

    Keep this guide current: when a script name, a path, or a step changes, update it here first — this is the document a human reaches for.
